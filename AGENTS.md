# Momento — contribution

Travailler dans le dépôt GitHub de référence de Momento, sur la branche principale, en préservant les changements du propriétaire. Pour du code, exécuter `pnpm test` puis `pnpm run build:pages` avant publication. Pour des documents seuls, relire le diff. Aucun force-push ; proposer une PR si nécessaire.

Supabase Auth gère les comptes. Le site suit le fournisseur e-mail natif et l’autorisation de créer de nouveaux comptes ; une fermeture des inscriptions doit laisser fonctionner la connexion existante. Les variables historiques de l’adaptateur D1 ne doivent pas fermer la cible Supabase. Conserver les tests de cohérence du mode de confirmation, des quotas, des sessions et des accès entre comptes. Le profil doit être complété avant les espaces membre.

Ne publier aucune clé, donnée personnelle ou détail d’infrastructure privé. Conserver les paramètres sensibles dans les services concernés. Ne modifier aucun autre projet. Les paramètres opérationnels sont conservés dans le suivi privé du projet.

Les mises à jour de routine sont autorisées après vérification. Vérifier aussi le résultat réellement servi par le site ; un push seul ne prouve pas un déploiement réussi. Décrire séparément les tests locaux, les vérifications des services et les essais sur appareils. La démonstration doit rester explicitement distincte des rencontres réelles.

Ne pas activer de service payant, de vente ou de rencontre réelle sans les validations correspondantes. La partie physique reste un teaser. Une PWA installable n’est pas une publication App Store ou Google Play. Voir les documents publics de suivi pour les limites fonctionnelles courantes.

Conserver le cadre d’application fixe demandé par le propriétaire : menu latéral, vues centrales, tiroir mobile et défilement interne pour les contenus longs. Garder l’identité romantique de Momento, des transitions qui ne retardent pas la navigation et la préférence de réduction des animations. Ne pas revenir à une longue page d’accueil. Ne jamais accélérer la navigation par un cache persistant de données privées.

Conserver les palettes pastel demandées : duo rose/bleu pour les visiteurs ; automatique selon le genre déclaré du profil (femme rose, homme bleu, autres choix duo), avec palette personnelle modifiable. Ne jamais déduire le genre du prénom, de la photo ou des envies de rencontre. Les couleurs ne modifient aucun droit et les préférences locales doivent rester séparées par compte.

Les alertes de fin d’appel doivent rester dans un petit encart sur la vidéo, sans voile sur la page, blocage des commandes ou déplacement automatique du focus. Le demandeur confirme le coût de sa prolongation avant l’envoi ; seul son accès est consommé après acceptation de l’invité. L’invité accepte gratuitement. Après ce premier accord explicitement annoncé, le même demandeur peut renouveler cet aparté encore actif sans nouvelle réponse du partenaire, en confirmant chaque coût. Ce droit local disparaît à la fin, au changement de personne ou au rechargement ; chacun peut quitter. Refus, annulation, expiration et réponse répétée ne doivent jamais créer de débit supplémentaire. Une modification du tarif ou du Premium ne peut pas augmenter silencieusement le coût autorisé.

Le socle serveur de prolongation reste désactivé jusqu’à validation des médias, rotations et droits. Les acteurs viennent d’Auth ; ne jamais accepter un payeur, rôle, Premium, solde ou environnement transmis par le navigateur. Débit prépayé et accès privé sont atomiques ; aucun achat bancaire de remplacement. Les opérations financières prennent les verrous de profil dans l’ordre des identifiants. Conserver la restitution du même accès après une réponse perdue, l’export des accords et les tests sur les deux sources de schéma. Ne pas créer de rencontres, crédits ou comptes de test dans le projet hébergé pour tester ces règles.
